# RK3568 (dayu200) 内核 CPU 调度器分析报告

> 平台: OpenHarmony 5.0.1-Release 自编译产物(2026-08-02 全量构建成功)
> 内核: Linux 5.10 rockchip 分支(`kernel/linux/linux-5.10`)+ OHOS rk3568 补丁
> 目的: 面向操作系统设计竞赛(内核方向),评估调度器现状与优化空间
> 源码位置: `~/2024204088/OHOS501/kernel/linux/linux-5.10`

---

## 1. 平台与内核现状

### 1.1 硬件特征(RK3568)

- 4x Cortex-A55 小核,**同构**,最高 1.8GHz,单簇(DIE0)
- 无大小核(不适用 EAS/CPU 迁移策略)、无 NUMA、无 SMT
- 形态: 开发板/平板场景,功耗敏感,UI 与音频实时性敏感

### 1.2 调度器构成(源码级盘点)

| 组件 | 状态 | 说明 |
|---|---|---|
| CFS(标准 5.10) | 启用 | fair.c(12288 行,含 WALT 改造),PELT 负载跟踪 |
| WALT | **启用且默认开** | walt.c,高通窗口负载跟踪;`sysctl_sched_use_walt_cpu_util=1`、`sysctl_sched_use_walt_task_util=1`,fair.c 主路径已接入(行 3943/6720/6763) |
| RTG(线程组调度) | 启用 | `kernel/sched/rtg/`,含 CGROUP/FRAME/DEBUG;接口 `/proc/sys/kernel/sched_rtg_ctrl` |
| RT 调度类 | 启用 | 标准 rt.c,push/pull 机制 |
| DL(deadline) | 启用 | 标准 deadline.c |
| core_ctl(核心管控) | **未启用** | 同构核无意义 |
| EAS(energy-aware) | 未启用 | 4x A55 同构,无收益(仅 rk3399 DTS 有 energy model) |

### 1.3 实际启用的关键配置(构建产物 `.config`)

```
CONFIG_PREEMPT_VOLUNTARY=y     # 非 FULL_PREEMPT —— 响应性主要短板
CONFIG_HZ=300                  # 非 1000
CONFIG_NO_HZ_IDLE=y            # 非 NO_HZ_FULL
CONFIG_SCHED_WALT=y            # WALT 开
CONFIG_SCHED_RTG=y             # RTG 开(+CGROUP/FRAME/DEBUG)
CONFIG_SCHED_AUTOGROUP=n       # 未开
CONFIG_RT_GROUP_SCHED=n        # 未开
CONFIG_CPU_ISOLATION=y + OPT   # rockchip isocpu 支持,可隔离核
CONFIG_SCHED_DEBUG/STATS=y     # 观测性良好
CONFIG_ENERGY_MODEL=y + SCHEDUTIL  # schedutil 调频,无 EAS
CONFIG_FAIR_GROUP_SCHED=y      # cgroup 公平组
```

### 1.4 OHOS 特有的调度生态(上层已就绪)

`foundation/resourceschedule/` 下已有完整场景化调度框架,通过内核接口驱动调度器:

- **frame_aware_sched**(帧感知调度): 通过 `sched_rtg_ctrl` 设置 UI 帧线程组
- **qos_manager**(QoS): 应用层 QoS 等级 → 线程优先级/RTG
- **soc_perf / ffrt / concurrent_task_controller**: 负载感知与并发控制

结论: 内核的 RTG/WALT 是给 OHOS 上层框架用的**基础设施**,优化空间很大。

## 2. 现状短板(按源码定位)

1. **抢占模型弱**: `CONFIG_PREEMPT_VOLUNTARY` 下,内核态长临界区会造成 UI/音频抖动;5.10 内核态路径长(网络、ext4、显示驱动),RT 线程抢占延迟偏高。
2. **唤醒路径陈旧**(fair.c:6121-6208): `wake_affine_idle` + `wake_affine_weight` 是 5.10 时代算法,无 6.x 的 EEVDF/`wake_affine` 优化,同构核上对交互线程不够激进。
3. **负载跟踪双轨制**: WALT 与 PELT 并存,仅按开关切换,无"交互线程 WALT / 批量线程 PELT"的自适应策略;WALT 初始负载 `init_task_load_pct=15` 等参数未针对 OHOS 场景标定。
4. **均衡粒度粗**: 单簇 4 核,周期性均衡(每 60ms idle 均衡 250ms 周期)仍可能造成无谓迁移与 cache 抖动;`newidle_balance` 无 idle 核倾向性优化。
5. **RT/IRQ 无隔离**: 无 isolcpus/isocpu 配置,音频 RT 线程与 IRQ 竞争同一核,`sched_rt_runtime` 默认 95% 上限可导致 RT 饿死保护触发。
6. **无 deadline 应用**: DL 调度类未用于多媒体实时任务(音频/合成),RTG 帧组也仅做到线程组聚合,未与频率/功耗联动。

## 3. 优化空间(分级)

### 3.1 配置级(改动小,见效快,1~2 周)

| 优化项 | 做法 | 预期收益 | 风险 |
|---|---|---|---|
| 开启 FULL PREEMPT | `CONFIG_PREEMPT=y` | UI/音频最大延迟显著下降 | 吞吐轻微下降,需回归 |
| HZ 300 → 1000 | `CONFIG_HZ_1000` | 定时器粒度提升,响应更细 | 功耗略增 |
| isolcpus 隔离 1 核 | cmdline `isolcpus=3`(或 isocpu 配置) | RT/IRQ 独占核,音频零抖动 | 少 1 个应用核 |
| 开启 SCHED_AUTOGROUP | `CONFIG_SCHED_AUTOGROUP=y` | 多前台任务互不干扰 | 无 |
| RT 带宽/组保护 | `sched_rt_runtime_us` 调优或 RT_GROUP_SCHED | 防止 RT 饿死、保护音频 | 需测试 |
| schedstats 保留 | 已开 | 诊断基线 | 无 |

### 3.2 参数级(运行时调优,零编译,可入 sysctl 配置文件)

- **延迟类**: `sched_latency_ns`(默认 6ms)、`sched_min_granularity_ns`、`sched_wakeup_granularity_ns` 按场景标定(低延迟 → 缩小)。
- **WALT 类**(walt.c sysctl): `sched_use_walt_cpu_util/task_util`、`sched_window_stats_policy`(max recent avg)、`sched_ravg_hist_size`、`sched_init_task_load_pct`。
- **RT 类**: `sched_rt_period_us`/`sched_rt_runtime_us`。
- **调频联动**: schedutil `rate_limit_us` 上下限,响应与功耗折中;WALT `freq_reporting_policy`。

### 3.3 代码级(竞赛主战场,3.4 节给出路线)

1. **唤醒路径优化**: 移植 6.x EEVDF(工作量中)或对 `wake_affine_idle` 增加对称/亲和改进(小改)。
2. **WALT 自适应策略**: 交互线程 WALT、批量线程 PELT 双轨决策;改进 `walt_find_best_target` 迁移策略。
3. **负载均衡裁剪**: 同构单簇下减少周期性均衡频次、`newidle_balance` 增加目标核倾向。
4. **RTG 深化**(与 OHOS 上层联动,特色亮点): 帧线程负载预测、RTG 与频率/温控联动、RTG 抢占策略。
5. **IPC 唤醒优化**(OHOS 特色): Binder/轻量 IPC 唤醒侧的调度提升(类似 Android binder boost),契合分布式场景。
6. **DL 应用于多媒体**: 音频线程转 DL 调度类,deadline 保证。
7. **可观测性**: 已有 sched tracepoints/sched_debug/schedstat,可补 RTG/WALT 专属 tracepoint,形成度量闭环。

### 3.4 建议路线(3 个月节奏)

- **阶段 1(1~2 周)**: 配置级 + 参数级优化,建基线(见第 4 节),产出第一个可对比版本。
- **阶段 2(4~6 周)**: 代码级小改(唤醒亲和、均衡裁剪、WALT 参数),逐项回归。
- **阶段 3(6~8 周)**: 主线——RTG 深化 或 EEVDF 移植(竞赛亮点),配合 frame_aware_sched/qos_manager 场景验证。
- **阶段 4(2 周)**: 优化落地到自编译镜像,烧录 dayu200 实测对比,整理实验数据成竞赛材料。

## 4. 实验与验收建议

### 4.1 量化基准(建议先跑基线)

| 指标 | 工具 | 目标 |
|---|---|---|
| 调度延迟/抖动 | cyclictest(mainline 移植或 busybox) | 最大延迟、p99 抖动 |
| 吞吐 | hackbench / schbench | 回归检测 |
| 进程切换开销 | lmbench(pipe/lat_ctx) | 对比 |
| UI 帧率 | OHOS 自带 framestats / trace | 丢帧率 |
| 音频卡顿 | 音频线程 RT 延迟采样 | 卡顿次数 |

### 4.2 验收方式

- 每个优化项: 基线与优化后数据对比表(至少 3 次取均值)。
- 全套改动最终打补丁到 `kernel/linux/patches/linux-5.10/rk3568_patch/` 或独立 patch 文件,保证可复现构建(我们已有自编译镜像作为基线)。

---

## 5. 结论

- 内核底子好: WALT/RTG/isocpu 基础设施齐全,OHOS 上层框架(帧感知/QoS)已就绪,优化具备生态支撑。
- 最大短板在抢占模型与唤醒/均衡路径的陈旧算法;配置级改动即可获得可见收益。
- 建议以"RTG 深化 + 唤醒优化"为竞赛主线,以 cyclictest/帧率/音频为度量,3 个月节奏推进。
